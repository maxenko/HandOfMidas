### Notes on directory choices

- **`crates/`**: All workspace members live under a single `crates/` directory.
  This keeps the root clean and makes glob patterns simple (`crates/*`).
- **`shaders/`**: WGSL shaders live inside `midas-render/shaders/`, NOT inside
  `src/`. They are not Rust code. They are included at compile time via
  `include_str!()`. See section 10.
- **`data/`**: Gitignored. Created at scaffold time so the app has a valid path
  on first run. The inner `candles/` directory is where mmap'd binary files go.
- **`tests/data/`**: Sample CSV files for integration tests. Checked into git.
- **`benches/`**: Root-level directory for workspace-wide criterion benchmarks.
  Not a separate crate — individual crates can also have `benches/` dirs later.
- **`plan/`**: Design documents. Already exists. Not built, not deployed.

# Use all available CPU cores for compilation
jobs = 0

[term]
# Color output in terminal
color = "always"

[registries.crates-io]
protocol = "sparse"
```

### 3.2 `rust-toolchain.toml`

```toml
[toolchain]
channel = "stable"
components = ["clippy", "rustfmt", "rust-src"]
targets = ["x86_64-pc-windows-msvc"]
```

### 3.3 Why these settings

| Setting | Rationale |
|---|---|
| `target-cpu=native` | Unlocks AVX2/SSE4.2 for glam SIMD math and bytemuck operations. This binary is not redistributed — it runs only on the dev machine. |
| `opt-level = 1` (dev root) | GPU data preparation code is unusable at opt-level 0. Level 1 gives ~5x speedup with minimal compile-time cost. |
| `opt-level = 2` (dev deps) | wgpu, iced, and tokio are painfully slow at opt-level 0. Since deps rarely recompile, the build-time cost is one-time. |
| `lto = "fat"` (release) | Cross-crate inlining across all 6 workspace crates. Critical for zero-cost abstractions at crate boundaries. |
| `codegen-units = 1` (release) | Maximizes LLVM optimization opportunities. Release builds are infrequent; compile time is acceptable. |
| `panic = "abort"` (release) | Eliminates unwinding tables. Smaller binary, slightly faster. We use tracing for error reporting, not panic recovery. |
| `strip = "symbols"` (release) | Removes debug symbols from the final binary. Use `release-debug` profile when profiling. |

## 4. Crate Dependency Graph

```
Simplified:

    midas-core          (leaf — IDs, Timeframe, CandleData trait, config, shared types)
        ↑
    midas-data          (depends on midas-core — storage, binary format, SoA buffers)
        ↑
    midas-chart         (depends on midas-core, midas-data — sans-IO chart logic + ChartScene)
        ↑
    midas-render        (depends on midas-core, midas-data, midas-chart — wgpu GPU pipelines)
    midas-feed          (depends on midas-core, midas-data — CSV import)
        ↑
    midas-app           (depends on all above — iced application shell)
```

### Dependency boundary rationale

| Boundary | Why it exists |
|---|---|
| `midas-core` has zero internal deps | Leaf crate. Shared types (IDs, events, config schema, timeframe enum, `CandleData` trait) that every other crate needs. Changing it recompiles everything, so it must be small and stable. |
| `midas-data` depends only on `midas-core` | Data storage is independent of rendering, chart logic, and GUI. It defines `CandleBuffer` (SoA layout, implements `CandleData`), binary file format, and mmap logic. Consumed by `midas-chart`, `midas-render`, and `midas-feed`. |
| `midas-chart` depends on `midas-core` + `midas-data` | Sans-IO chart core. Contains `ChartState`, `ChartScene` (intermediate representation), `ChartInput`, `ChartEvent`/`ChartAction` state machine, `Camera2D`, coordinate transforms, `DirtyFlags`/`DirtyTracker`, horizontal levels, crosshair state, zoom/pan/auto-scale/momentum logic. Has zero GPU or framework dependencies. Consumes data through the `CandleData` trait. |
| `midas-render` depends on `midas-core` + `midas-data` + `midas-chart` | The renderer reads `ChartScene` (produced by `midas-chart`) to build GPU instance buffers. It does NOT depend on iced — it produces wgpu render passes that iced's `Shader` widget consumes. This decoupling allows headless rendering for tests. |
| `midas-feed` depends on `midas-core` + `midas-data` | Feed produces data (writes `CandleBuffer`, writes binary files). It does NOT depend on chart logic, rendering, or GUI. |
| `midas-app` depends on all | The application shell wires everything together: loads data via `midas-feed`, runs chart logic via `midas-chart`, passes scene to `midas-render`, runs inside iced. It is the only crate that knows about iced. |

### Circular dependency check

No cycles exist. The dependency order is strictly:
`midas-core` < `midas-data` < `midas-chart` < `midas-render` < `midas-app`
`midas-core` < `midas-data` < `midas-feed` < `midas-app`

Each arrow points from dependent to dependency (higher to lower). No crate at a
lower level depends on a crate at a higher level.

## What is this project?

Hand of Midas is a native desktop stock charting application written in pure Rust.
It renders 20+ simultaneous charts at 60fps using custom wgpu 27 GPU pipelines inside
an iced 0.14 GUI shell. Target platform: Windows 11 (x86_64).

## Workspace structure

This is a Cargo workspace with 6 crates under `crates/`:

| Crate | Type | Purpose | Internal deps |
|---|---|---|---|
| `midas-core` | lib | Shared types, IDs, events, config schema, `CandleData` trait | none (leaf) |
| `midas-data` | lib | SoA candle buffers, binary format, mmap, LOD | midas-core |
| `midas-chart` | lib | Sans-IO chart core: ChartState, ChartScene, Camera2D, interactions, dirty flags | midas-core, midas-data |
| `midas-render` | lib | wgpu GPU rendering pipelines, reads ChartScene | midas-core, midas-data, midas-chart |
| `midas-feed` | lib | CSV import, data provider trait, future streaming | midas-core, midas-data |
| `midas-app` | bin | iced application shell, ties everything together | all above |

Dependency flows strictly downward. No circular dependencies.

## Build commands

```bash
# Build entire workspace
cargo build --workspace

# Run the application
cargo run -p midas-app

# Run with logging
RUST_LOG=midas=debug cargo run -p midas-app

# Run all tests
cargo test --workspace

# Run clippy
cargo clippy --workspace -- -D warnings

# Format code
cargo fmt --all

# Release build (slow compile, fast binary)
cargo build --workspace --release

# Profiling build (release + debug symbols)
cargo build --workspace --profile release-debug
```

## Key conventions

### Code style
- Rust 2021 edition, stable toolchain
- `snake_case` for functions, variables, modules
- `PascalCase` for types, traits, enum variants
- `SCREAMING_SNAKE_CASE` for constants
- Max line width: 100 characters (rustfmt default)
- Prefer `thiserror` for library error types, `anyhow` only in midas-app
- All public items must have doc comments (`///`)
- No `unwrap()` in library crates — use `?` or explicit error handling
- `unwrap()` is acceptable only in tests and main.rs during early development

### Architecture rules
- `midas-chart` is the sans-IO chart core. It has zero GPU or framework dependencies. All chart logic (state, interactions, zoom/pan, auto-scale) lives here.
- `midas-chart` consumes data through the `CandleData` trait (defined in `midas-core`), not concrete types.
- `midas-render` reads `ChartScene` (produced by `midas-chart`) to build GPU primitives. It does NOT depend on iced.
- `midas-core` must remain small and stable. Changes recompile the entire workspace.
- GPU data structs must be `#[repr(C)]` and derive `bytemuck::Pod + Zeroable`.
- SoA (Structure of Arrays) layout for candle data, not AoS.
- Shaders are WGSL files in `crates/midas-render/shaders/`, included via `include_str!()`.
- Configuration is TOML (not JSON, not YAML).

### File locations
- Shaders: `crates/midas-render/shaders/*.wgsl`
- Runtime data: `data/` (gitignored)
- Binary candle files: `data/candles/<SYMBOL>/<timeframe>.candles`
- User config: `data/config.toml`
- Test fixtures: `tests/data/`
- Design documents: `plan/`

### Error handling pattern
```rust
// In library crates (midas-core, midas-data, midas-chart, midas-render, midas-feed):
use thiserror::Error;

#[derive(Debug, Error)]
pub enum DataError {
    #[error("file not found: {path}")]
    FileNotFound { path: String },
    #[error("invalid binary format: {0}")]
    InvalidFormat(String),
    #[error(transparent)]
    Io(#[from] std::io::Error),
}

// In midas-app (binary crate):
use anyhow::{Context, Result};
fn load_data() -> Result<()> {
    let buf = midas_data::load("AAPL")
        .context("failed to load AAPL candle data")?;
    Ok(())
}
```

### GPU data struct pattern
```rust
#[repr(C)]
#[derive(Copy, Clone, Debug, bytemuck::Pod, bytemuck::Zeroable)]
pub struct CandleInstance {
    pub x: f32,
    pub body_top: f32,
    pub body_bottom: f32,
    pub wick_top: f32,
    pub wick_bottom: f32,
    pub width: f32,
    pub color: [f32; 4],
}
```

## 8. Dev Workflow

### 8.1 Running during development

```bash
# Standard dev run with logging
RUST_LOG=midas=debug cargo run -p midas-app

# Quieter run (only warnings and errors)
RUST_LOG=midas=info,wgpu=warn cargo run -p midas-app

# Release-speed run for performance testing
cargo run -p midas-app --release
```

### 8.2 Fast incremental builds

Rust does not support hot-reload, but incremental compilation is fast for
workspace crates (typically 1-5 seconds for a single-crate change).

Tips for fast iteration:
- **Change leaf crates last**: Editing `midas-core` recompiles everything.
  Editing `midas-app` recompiles only `midas-app`.
- **Use `cargo check`** instead of `cargo build` when you only want to verify
  the code compiles (skips codegen — much faster).
- **Parallel compilation**: The workspace dependency graph allows `midas-render`
  and `midas-feed` to compile in parallel since they don't depend on each other.
  `midas-chart` must compile before `midas-render` (which depends on it).
- **Avoid touching Cargo.toml**: Adding/removing dependencies triggers a full
  dependency resolution and often a full rebuild.

```bash
# Fast type-check (no codegen)
cargo check --workspace

# Check only the crate you're working on
cargo check -p midas-render
```

### 8.3 IDE setup: rust-analyzer

Create `.vscode/settings.json` (or equivalent for your editor):

```json
{
    "rust-analyzer.cargo.features": "all",
    "rust-analyzer.check.command": "clippy",
    "rust-analyzer.check.extraArgs": [
        "--workspace",
        "--",
        "-D", "warnings"
    ],
    "rust-analyzer.diagnostics.experimental.enable": true,
    "rust-analyzer.inlayHints.parameterHints.enable": false,
    "rust-analyzer.inlayHints.typeHints.enable": true,
    "rust-analyzer.procMacro.enable": true,
    "rust-analyzer.cargo.buildScripts.enable": true,
    "files.watcherExclude": {
        "**/target/**": true,
        "**/data/**": true
    },
    "[rust]": {
        "editor.formatOnSave": true,
        "editor.defaultFormatter": "rust-lang.rust-analyzer"
    }
}
```

Key settings explained:
- **`check.command: clippy`**: rust-analyzer runs clippy instead of plain `check`,
  catching more issues in real-time.
- **`files.watcherExclude: target`**: Prevents the IDE from watching the massive
  `target/` directory (thousands of build artifacts).
- **`formatOnSave`**: Automatically runs `rustfmt` on save.

### 8.4 Recommended development loop

1. Edit code in your IDE.
2. Save (auto-formats with rustfmt, rust-analyzer runs clippy in background).
3. Fix any inline diagnostics.
4. `cargo run -p midas-app` to see visual results.
5. `cargo test -p <crate>` to run targeted tests.

### 8.5 Benchmarks (once criterion benchmarks are added)

```bash
# Run all benchmarks
cargo bench --workspace

# Run a specific benchmark
cargo bench -p midas-data --bench data_bench

# Compare against baseline
cargo bench --workspace -- --save-baseline main
# ... make changes ...

## 10. Shader Files

### 10.1 Location

All WGSL shader files live in:

```
crates/midas-render/shaders/
```

They are NOT in `src/` because they are not Rust code. They are GPU programs
written in WGSL (WebGPU Shading Language).

### 10.2 Naming convention

```
<pipeline_name>.wgsl
```

Planned shaders:
| File | Pipeline | Purpose |
|---|---|---|
| `candle.wgsl` | CandlePipeline | Instanced candlestick bodies + wicks |
| `volume.wgsl` | VolumePipeline | Instanced volume bars |
| `line.wgsl` | LinePipeline | Line strips (grid, indicators) |
| `hline.wgsl` | HLinePipeline | Horizontal price levels |
| `crosshair.wgsl` | CrosshairPipeline | Crosshair overlay |
| `rect.wgsl` | RectPipeline | General filled rectangles |
| `msdf.wgsl` | TextPipeline | MSDF text rendering |

### 10.3 Inclusion method: `include_str!()`

Shaders are compiled into the binary at Rust compile time using `include_str!()`.

```rust
// In crates/midas-render/src/pipelines/candle.rs:
const SHADER_SRC: &str = include_str!("../../shaders/candle.wgsl");

// Used when creating the wgpu pipeline:
let shader_module = device.create_shader_module(wgpu::ShaderModuleDescriptor {
    label: Some("candle_shader"),
    source: wgpu::ShaderSource::Wgsl(SHADER_SRC.into()),
});
```

### 10.4 Why `include_str!()` and not runtime file loading

| Approach | Pros | Cons |
|---|---|---|
| `include_str!()` | No runtime I/O. No missing file errors. Binary is self-contained. Compile error if shader file missing. | Must recompile to change shaders. |
| Runtime file load | Can edit shaders without recompiling. Hot-reload possible. | Runtime errors if file missing. Need to ship shader files alongside binary. Path resolution issues. |

For a production desktop app, `include_str!()` is correct. The shaders are part
of the program, not user-configurable resources.

**Development convenience**: During shader development (Phase 1), you can
temporarily add a `cfg(debug_assertions)` path that loads from disk for faster
iteration, then remove it:

```rust
#[cfg(debug_assertions)]
fn load_shader() -> String {
    std::fs::read_to_string("crates/midas-render/shaders/candle.wgsl")
        .unwrap_or_else(|_| include_str!("../../shaders/candle.wgsl").to_string())
}

#[cfg(not(debug_assertions))]
fn load_shader() -> &'static str {
    include_str!("../../shaders/candle.wgsl")
}
```

This is optional and should be removed before release.

## Appendix C: Known Issues and Notes

### iced 0.14 + wgpu 27 compatibility

**RESOLVED**: iced 0.14 uses wgpu 27 internally. Our workspace dependency
`wgpu = "27"` matches exactly. There should be no duplicate wgpu types in
the dependency tree.

**Verification step**: After the first `cargo build`, run:
```bash
cargo tree -p iced | grep wgpu
```
Confirm that only wgpu 27.x appears. If a future iced patch bumps its internal
wgpu version, update our workspace `wgpu` dependency to match.

**Important**: iced 0.13 used wgpu 0.19, which is completely incompatible.
iced 0.14 introduced the new `shader::Pipeline` associated type pattern
(replacing the old `Storage`-based approach) and upgraded to wgpu 27.
Do NOT downgrade to iced 0.13.

### Windows linker performance

On Windows with MSVC, linking can be slow. If link times exceed 5 seconds in
dev builds, consider adding to `.cargo/config.toml`:

```toml
# Experimental: use lld linker for faster dev linking (requires lld installed)
# [target.x86_64-pc-windows-msvc]
# linker = "lld-link"
```

Install lld via `cargo install lld` or through LLVM. This is optional and can
cause issues with some Windows SDK versions.

### GPU validation layers

wgpu has built-in validation that catches GPU API misuse. In debug builds, this
is enabled by default. If you see validation errors in the console (yellow/red
messages from wgpu), they are real bugs in the rendering code, not false positives.

To see maximum validation output:
```bash
RUST_LOG=wgpu=debug cargo run -p midas-app
```
